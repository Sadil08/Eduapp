## Summary
The service has a recognisable layered architecture with Redis caching and Spring Async wiring in place, but several concrete, load-bearing problems exist that will manifest under production traffic. The most severe are a DDL migration that runs on every startup (causing full-table ACCESS EXCLUSIVE locks in PostgreSQL), a grossly under-provisioned async executor (max 5 threads for what the architecture describes as AI workloads), and pervasive unbounded list endpoints that will OOM the JVM or time out as data grows. These are not theoretical risks — they are patterns that predictably fail once concurrent users and data volume increase beyond a trivial threshold.
## Concerns
### [CRITICAL] db — src/main/java/com/eduapp/backend/config/DatabaseMigrationRunner.java
Multiple ALTER TABLE statements execute on every application startup via CommandLineRunner. In PostgreSQL, ALTER COLUMN ... TYPE TEXT acquires an ACCESS EXCLUSIVE lock, blocking all concurrent reads and writes on the questions table for the duration of the operation. On a table with meaningful data this can take seconds to minutes. In a multi-instance deployment with rolling restarts this will cause repeated table lockouts. There are no idempotency guards — the ALTER is attempted unconditionally even when columns are already TEXT, creating unnecessary lock acquisitions every time.

**Fix:** Replace this entirely with a proper schema migration tool (Flyway or Liquibase). Flyway's versioned migrations are idempotent by design and only execute once. If a manual approach must be kept, at minimum wrap each statement with a check: ALTER TABLE ... ALTER COLUMN ... TYPE TEXT only when information_schema.columns.data_type != 'text'.
### [CRITICAL] concurrency — src/main/java/com/eduapp/backend/config/AsyncConfig.java
The async executor is configured with corePoolSize=2, maxPoolSize=5, queueCapacity=100. The architecture explicitly describes AI-analysis workloads running through this pool. AI calls are typically slow (hundreds of milliseconds to several seconds). With a max of 5 concurrent workers and a bounded queue of 100, under moderate load — roughly more than 105 in-flight AI requests — Spring will throw TaskRejectedException, causing hard failures for end users. The pool will also saturate at very low concurrency (5 simultaneous users running analyses), meaning sequential queuing will dominate latency.

**Fix:** Size the pool to match expected concurrency. For I/O-bound AI calls, a corePoolSize of 20–50 with maxPoolSize of 100 and a queueCapacity of 500–1000 is more appropriate. Also set a meaningful RejectedExecutionHandler (e.g., CallerRunsPolicy or a custom handler that returns HTTP 503) to avoid silent task drops.
### [HIGH] db — src/main/java/com/eduapp/backend/controller/AIAnalysisController.java
GET /api/ai-analyses calls aiAnalysisService.findAll() which returns the full List<AIAnalysis> with no LIMIT, OFFSET, or pagination contract. As rows accumulate this will (a) execute a full table scan, (b) materialise the entire result set in JDBC, (c) hold it in JVM heap, and (d) serialise it all to JSON. At tens of thousands of records this causes GC pressure and multi-second response times; at hundreds of thousands it causes OOMEs. The same pattern likely exists across other getAll() endpoints in AdminBundleController, AdminUserController, and similar controllers given the architecture.

**Fix:** Replace findAll() with a paginated repository method: Page<AIAnalysis> findAll(Pageable pageable). Accept ?page= and ?size= query parameters (default size 20, max 100). Return a Page<> or a custom PagedResponse DTO that includes totalElements and totalPages so clients can navigate.
### [HIGH] db — src/main/java/com/eduapp/backend/controller/AdminUserController.java, AdminBundleController.java, AdminCustomBundleController.java
All admin list endpoints visible in the codebase return full List<T> collections with no pagination. Admin dashboards are frequently misused as background jobs or polled by scripts, amplifying the unbounded query impact. AdminCustomBundleController.getPendingApproval() and getAll() endpoints will load every bundle record on each call. Under a multi-tenant educational platform with thousands of students and bundles this will cause the DB to perform full scans and the JVM to hold large result sets in memory.

**Fix:** Apply Pageable to all collection-returning repository calls. Enforce a maximum page size server-side. For admin aggregate views, use SQL GROUP BY + COUNT queries rather than loading full entity graphs.
### [HIGH] caching — src/main/java/com/eduapp/backend/controller/AdminDashboardController.java
GET /api/admin/dashboard/revenue calls studentBundleAccessService.calculateTotalRevenue() synchronously on every request with no visible caching annotation. Revenue aggregation typically involves a full or near-full table scan with SUM across the student_bundle_access table. If this endpoint is called frequently (e.g., polled by a dashboard UI or monitoring) it will generate repeated expensive aggregation queries under load, competing with user-facing queries for DB resources.

**Fix:** Annotate calculateTotalRevenue() with @Cacheable(value = "revenueCache", key = "'total'") and configure a TTL of 60–300 seconds in RedisConfig. Since Redis is already configured in the project, this requires minimal effort. Alternatively, compute this metric asynchronously on a schedule and cache the result.
### [HIGH] coupling — src/main/java/com/eduapp/backend/config/AsyncConfig.java (and implied AI service layer)
The architecture states AI analysis is processed asynchronously via the Spring @Async executor, but the executor feeds into an HTTP response path (AIAnalysisController returns ResponseEntity synchronously). If the calling thread polls or blocks for the async result this is synchronous blocking I/O dressed as async. Additionally, there is no evidence of a message queue (Kafka, RabbitMQ, SQS) between the web layer and AI processing. This creates tight temporal coupling — the web server thread (or async thread) is held for the duration of external AI API latency, preventing horizontal scaling of just the AI processing tier.

**Fix:** Decouple AI job submission from result delivery using a message queue. POST /analyse returns immediately with a job ID (202 Accepted). A separate consumer service pulls from the queue, calls the AI API, and writes results back. Clients poll GET /api/ai-analyses/{id} for status. This allows independent scaling of the AI worker pool.
### [MEDIUM] connection — src/main/java/com/eduapp/backend/config/ (application configuration, not explicitly shown)
No explicit HikariCP connection pool configuration is visible in the provided files. Spring Boot's HikariCP defaults (maximumPoolSize=10) are tuned for development, not production. Given the async thread pool can have up to 5 threads, plus Tomcat's default of 200 worker threads, the application could attempt more concurrent DB connections than the pool allows, causing threads to block waiting for connections. This is compounded by the lack of a connection timeout / leak detection threshold configuration.

**Fix:** Add explicit HikariCP settings to application.properties: spring.datasource.hikari.maximum-pool-size=20, spring.datasource.hikari.minimum-idle=5, spring.datasource.hikari.connection-timeout=30000, spring.datasource.hikari.leak-detection-threshold=60000. Size the pool to match expected concurrent query load, not just thread count.
### [MEDIUM] coupling — Architecture (Supabase S3 via boto3 Python scripts)
The architecture notes that binary media is stored in Supabase S3-compatible storage accessed via boto3 Python scripts. There is no circuit breaker, retry with exponential backoff, or timeout configuration visible for these calls. If Supabase S3 is slow or unavailable, the calling Java thread will block indefinitely (or until the OS socket timeout, which can be minutes). Under load, all worker threads can become blocked on a degraded external dependency, causing complete service unavailability.

**Fix:** Wrap all S3 calls with Resilience4j CircuitBreaker and Retry annotations. Set aggressive connect and read timeouts (e.g., 5s / 30s). For image uploads, make the flow async — accept the upload, store to a local temp location or pre-signed URL, return immediately, and process/move to S3 asynchronously. Use the dead-letter queue pattern for failed uploads.
### [MEDIUM] db — TestDB.java
TestDB.java uses raw DriverManager.getConnection() with a hardcoded plaintext password. While this appears to be a one-off utility script, its presence in the repository indicates it may be invoked in non-development contexts. DriverManager creates a new physical connection per call with no pooling. If this or similar code paths are invoked at scale (e.g., in a health-check script called by orchestration), it will create a connection storm against PostgreSQL.

**Fix:** Remove this file from the repository entirely or move it to a test-only scope that is excluded from production builds. Never use DriverManager for application code — all DB access must go through the DataSource/connection pool. Credentials must be externalised via environment variables, never hardcoded.
### [LOW] caching — src/main/java/com/eduapp/backend/config/RedisConfig.java
The ObjectMapper used for Redis serialization enables activateDefaultTyping with polymorphic type validator. This embeds Java class names in every cached value, making the cache tightly coupled to the application's internal class structure. Any refactor or rename of a cached class will produce cache deserialization failures at runtime. The polymorphic type information also inflates cache payload sizes, increasing Redis memory usage and serialization overhead.

**Fix:** Use a DTO-based caching strategy — only cache simple, stable DTOs rather than JPA entities. Replace activateDefaultTyping with explicit @JsonTypeInfo on only the specific polymorphic types that require it. Consider using a non-polymorphic serializer like Jackson2JsonRedisSerializer with a concrete target type for each cache region.
